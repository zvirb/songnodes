## 2026-10-24 - Pre-computing edge transition costs in A* search loops
**Learning:** In graph pathfinding algorithms (such as A* for DJ setlists), evaluating static transition properties (e.g. key compatibility, BPM difference penalties, synthetic edge checks) during neighbor expansion inside a progressive relaxation loop causes millions of redundant function calls and dictionary lookups. Pre-computing a static adjacency structure (`prepare_adjacency`) before starting the search loop reduces search execution time by ~50%.
**Action:** When working with A* or graph search algorithms that perform multiple search attempts or relaxations over a fixed graph, pre-calculate static edge costs and metadata once into an optimized adjacency lookup structure before entering the priority queue expansion loop.

## 2026-10-26 - Target metadata pre-computation and regex memoization in track candidate matching
**Learning:** In metadata resolution and provider enrichment workflows, comparing a single target track against $N$ candidate tracks repeatedly calls title parsing, artist key normalization, ISRC cleaning, and regex compilation for the target track on every single iteration. Pre-parsing the target track's metadata once before candidate iteration combined with module-level regex compilation and `@lru_cache` memoization reduces matching time by >60%.
**Action:** When evaluating a target entity against lists of candidates in loops, pre-compute all static properties of the target entity before entering the loop, pass them as optional arguments, and pre-compile/memoize regex-heavy string normalization operations.

## 2026-10-29 - Pre-computing 24x24 Camelot key compatibility matrices
**Learning:** Force-directed graph layouts and harmonic link calculations evaluate Camelot key compatibility and link distance multipliers on every force simulation tick. Performing string slicing, `parseInt`, and condition checks inside the tick loop creates unnecessary CPU overhead. Pre-computing a static 24x24 2D matrix (`KEY_COMPATIBILITY_TABLE` and `HARMONIC_DISTANCE_TABLE`) at module initialization provides O(1) table lookups and speeds up calculations by ~45%.
**Action:** For fixed-domain relationship definitions (like the 24 Camelot keys on the harmonic wheel), pre-compute a static 2D lookup matrix at module initialization time rather than parsing and computing relationships dynamically inside hot simulation loops.
